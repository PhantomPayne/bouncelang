##### Q1 — `Option<T>` model: `:some/:none` vs `(T & :true) | :false`

**Full question:** `atoms-and-unions.md §7` defines `Option<T>` as `:some { value: T } | :none`, while `02-data-structures.md §3` defines it as `(T & :true) | :false` with `T?` sugar. Which definition is canonical, and how should the draft specs be updated?

**Option A (v2-aligned):** Update `atoms-and-unions.md` and `modules-and-imports.md` to use `(T & :true) | :false` as the canonical `Option<T>` model. Remove the `:some/:none` definition. Add `T?` as syntactic sugar. Document flow-sensitive narrowing in `if`/`match`.
- Core principles advanced: **Safety** (no `.value` unwrap possible — removes a class of "unwrap on None" bugs), **DX** (natural `if name { }` works, no special `Option` syntax to learn), **Understandability** (consistent with `Bool = :true | :false` already in the spec)
- Core principles compromised: Minor **Understandability** cost — `:some/:none` is familiar from Rust/Swift/Haskell; `(T & :true) | :false` is a new pattern

**Option B:** Keep `:some/:none` as canonical; update `02-data-structures.md` to match. The tags model would be treated as an internal implementation detail.
- Core principles advanced: **Understandability** (familiar to developers from other languages)
- Core principles compromised: **Safety** (`.value` access pattern re-introduced; DX (requiring `.value` unwrapping vs `if x { use(x) }`; reverts a v2 design decision

**Option C:** Keep both. `:some/:none` for the named union; `:true/:false` for the truthiness model. `Option<T>` is `:some { value: T } | :none`; `if x` checks truthiness via `:true/:false`.
- Core principles advanced: **Understandability** (familiar form preserved)
- Core principles compromised: **Consistency** ("One mechanism per concept" — two incompatible optionality systems); **Safety** (partial unwrap risk returns)

##### Q7 — `catch` keyword usage

**Full question:** `07-concurrency.md §4` and `04-effects-and-handlers.md §7` use `try { body } catch { err => ... }` syntax. `error-handling.md §1` says there is no `catch` keyword. Which is correct, and what is the v2 syntax for catching any error?

**Option A (v2-aligned):** Update both files to use the correct `try expr { arms }` syntax with a wildcard arm for any error. The wildcard error arm uses a bare binding name: `err => IO.eprintln("error: {err}")`.
- Core principles advanced: **Consistency** (one error-handling mechanism); **Understandability** (no separate keyword to learn)
- Core principles compromised: None

**Option B:** Introduce `catch { err => ... }` as sugar for the wildcard error arm. Update `error-handling.md` to document it.
- Core principles advanced: Familiarity for developers from other languages
- Core principles compromised: **Consistency** ("One mechanism per concept" — adds a second error-handling surface); **Anti-priority** (feature parity with other languages is explicitly an anti-priority)

##### Q4 — `NetworkError(e)` positional destructuring

**Full question:** `error-handling.md §4` uses `NetworkError(e)` to bind the whole error struct to `e`, then spreads it. No other spec establishes this syntax. What is the correct way to write "bind a whole error value and then spread its fields"?

**Option A (v2-aligned):** Replace `NetworkError(e) =>` with named field destructuring. Since the goal is to spread all fields into a new error with one field changed, name the specific fields and rebind them directly:
```bounce
NetworkError { url, status, message } => raise(NetworkError {
    url, status, message: "fetching user {id}: {message}",
})
```
- Core principles advanced: **Consistency** (uses the established named-field pattern); **Understandability** (field names are explicit)
- Core principles compromised: Slight verbosity when errors have many fields

**Option B:** Introduce `ErrorType as binding` syntax to bind the whole error struct by name while still using named-field pattern matching elsewhere.
- Core principles advanced: Ergonomics for large error structs
- Core principles compromised: **Consistency** (adds a new pattern form); scope of change larger than the question warrants

#### Rec-1 — `error` declaration syntax (contradiction)

**Finding:** R1-F2. `04-effects-and-handlers.md` used `error X { fields }` (no `=`); `error-handling.md` used `error X = { fields }` (with `=`).

**Decision:** The `=` form is canonical. It is consistent with `type X = { ... }` and `nominal type X = ...`. The `04-effects-and-handlers.md` example was incorrect.

**Change:** Fixed `error NotFoundError { id: Int }` → `error NotFoundError = { id: Int }` and `raise NotFoundError { id }` → `raise(NotFoundError { id })` in `04-effects-and-handlers.md` §2.1.

**Discarded:** The no-`=` form — inconsistent with all other type declaration patterns.

---

#### Rec-2 — Boolean operators and `if`/`else` as expression

**Finding:** R2-F10 (boolean operators not defined), R1-F10 (`if`/`else` expression status not stated).

**Decision:** Add explicit documentation to `01-primitives.md` §3. `&&`, `||`, `!` are short-circuit boolean operators. `if`/`else` is an expression. An `if` without `else` has type `()`.

**Change:** Added "Boolean Operators & Control Flow Expressions" subsection to `01-primitives.md` §3.

---

#### Rec-3 — Unit type `()` and block sequencing

**Finding:** R1-F4, R2-F8.

**Decision:** Define `()` in `02-data-structures.md` §6 (Tuples) as the empty tuple — a type with exactly one value. Document block sequencing: a block returns the value of its last expression.

**Change:** Added "The Unit Type `()`" subsection to `02-data-structures.md` §6.

---

#### Rec-4 — Lambda syntax and interface `self`

**Finding:** R1-F6, R1-F7, R2-F7.

**Decision:** Add "Function Literals (Lambdas)" subsection to `generics-and-type-system.md` §2 documenting `{ x => expr }` as the only anonymous function literal syntax. Add clarifying paragraph to §3 stating `self` in interface methods means the implementing type.

**Change:** Added to `generics-and-type-system.md` §2 and §3.
